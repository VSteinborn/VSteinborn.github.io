# Motivation
It seems like not a day can go by where we don't hear about AI on the internet lately.

Most of the discourse regarding AI focuses on specific tools from providers that you 
can access by visiting their website.

However, these tools are often not free or require you sending your text conversation 
or other data to the provider to make use of the tool.
This last point is especially problematic if you work in a setting where personal data or 
intellectual property cannot (or should not) be transferred out of an organization.

A solution to this dilemma is to run the AI model on your own computer using open-source models.
There are multiple ways of doing this, in this post I will show how 
you can use [Ramalama](https://ramalama.ai/) to run models in OCI containers.

{{ character(name="pineapple", body="OCI containers are virtualised operating systems that work 
in a manner that is standardized between devices.") }}

The main motivation for using OCI containers is that you don't have to worry about 
changing configurations if you decide to move to another device or cloud provider, 
this keeps the setup clean and reproducible.

This post is intended to outline some lessons learned in getting Ramalama running 
so that you can avoid the same pitfalls I had.

## Advantages
- Ramalama and open models are free and open-source
- You keep your data local and private
- Open-source models and software can be modified and audited
- The models are containerized for portability and security

## Things to keep in mind
- Some models are quite large and require a lot of memory 
- Some models (especially large models) can consume a lot of electricity to run

{{ character(name="pineapple", body="If the model requires more memory than your system 
is able to provide, you unfortunately can't run the model without changing your hardware 
or how the model is loaded into memory.") }}

# Notes on Setup
I will specifically focus on running Ramalama (version 0.16.0) for text completion 
in the [Zed IDE](https://zed.dev/) (version 0.223.3), however you can use Ramalama 
for other applications as well.

For this setup I am using a computer running [Fedora Linux](https://fedoraproject.org/) 
with the default `dnf` package manager, an NVIDIA graphics card and with Podman installed.

> This post will not be discussing how to setup agentic features or tools.

# Setup

## Install Ramalama

I started off with installing Ramalama using the information provided in the official 
[GitHub Repository](https://github.com/containers/ramalama). To do this I ran:

```bash
sudo dnf install ramalama
```

## Install NVIDIA Container Toolkit

Subsequently, because I am using an NVIDIA graphics card, I had to install the `nvidia-container-toolkit`
to enable CUDA support in containers.

This is where I ran into my first issue, because no `nvidia-container-toolkit` package exists in the 
default Fedora repositories.

To overcome this, I searched the `dnf` repositories via `dnf search nvidia-container-toolkit` and found 
a package named `golang-github-nvidia-container-toolkit` from the Fedora Project, which pointed to the 
official NVIDIA GitHub repository for the advertised `nvidia-container-toolkit` package.

I decided that this is a sufficiently trustworthy source for my use case, however you can also 
install the package from the NVIDIA repository directly, but this will require you adding 
a new repository to `dnf`.

In my case I ran:

```bash
sudo dnf install golang-github-nvidia-container-toolkit
```

## Generate CDI Specification File

With the NVIDIA Container Toolkit we have to generate a CDI (Container Device Interface) Specification File 
according to the Ramalama installation guide. To do this, simply run:

```bash
sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml
```

You can check if everything worked correctly by running:

```bash
nvidia-ctk cdi list
```

This should return a list of CDI devices. 

> According to the Ramalama documentation, the CDI Specification 
> file needs to be updated each time the driver is updated or if the GPU configuration changes, 
> so be aware of breaking changes.

## Serving a Model With Ramalama 

Once Ramalama is installed and configured, pulling and serving models is relatively simple.
For example, to pull the open mistral 7B model, simply run:

```bash
ramalama pull mistral
```

This will pull the default mistral model specified in the Ramalama configurations.
You can however pull specific models from a wide range of model registries, 
including Huggingface and Ollama. To serve the pulled model, simply run:

```bash
ramalama --runtime llama.cpp serve -p 8080 mistral
```

This runs the mistral model using the ``llama.cpp`` inference runtime 
(Ramalama also supports `vllm`) and makes the model accessible locally on port 8080.
For this article we use `llama.cpp`.

Before moving on, make note of a line that reads something along the lines of:
`main: server is listening on http://0.0.0.0:8080`, for example, when serving the model.
Make note of the `http` address, this is where the model is accessible locally.


## Making the Model Accessible in Zed

In the Zed IDE, open the `settings.json` file by opening the top ribbon menu in the top 
left window, click on `Zed`->`Open Settings` and then `Edit in settings.json`.
In `settings.json` add the following `"language_models"` key-value pair:

```json
{
 "telemetry":{...}, <- Placeholder field
 "auto_update":{...}, <- Other placeholder field
 "language_models": {
   "openai_compatible": {
     "Ramalama": { <- Custom name
       "api_url": "http://0.0.0.0:8080/v1", <- this is where you serve your model
       "available_models": [
         {
           "name": "Mistral-7B-Instruct-v0.3", <- Custom name
           "display_name": "Mistral-7B-Instruct-v0.3", <- Custom name
           "max_tokens": 32768 , <- It will be explained how to get this number
         },
       ],
     },
   },
 },
}
```

- `"api_url"`: make sure that this is the same as what is printed to the 
terminal after serving the model, with a final `/v1`.

{{ character(name="pineapple", body="The final `/v1` endpoint may be different if you decided to use
`vllm` instead of `llama.cpp`. Make sure to check the documentation of the 
service that you decide to use.") }}

- `"max_tokens"`: To get the `"max_tokens"` run the `ramalama inspect` command and look for a 
line with the word `context_length`:

```bash
ramalama inspect --all mistral | grep context_length
```

This command will tell you the maximum amount of tokens your model (in this case mistral) 
can accept as context.

## API Key

At this point, if you try to generate text with Zed, the editor may complain that
no API key is configured. If this happens, go to the model selection tab (next to
the send chat button in the agent panel), select `Configure` and type `none` for 
the Ramalama API key and save.

# Closing Thoughts

If you did all this, Zed should now be able to generate text in-line or using the 
chat window via Ramalama.
You can also chat with GPU support, which may even be faster than 
using an external paid service. In addition, you get to keep control of your data.
